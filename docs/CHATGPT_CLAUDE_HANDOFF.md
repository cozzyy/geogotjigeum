# CHATGPT → CLAUDE HANDOFF — 기획에서 개발로 넘기는 표준 절차

## 1. 목적
ChatGPT는 기획자/PM, Claude는 개발자를 기본 역할로 한다. 둘은 서로의 대화 기억에 의존하지 않고 GitHub의 문서·Issue·PR을 통해 업무를 인수인계한다.

기본 원칙은 **사용자의 승인 시간을 아끼되, 중요한 결정은 사용자에게 남긴다**는 것이다.

핵심 흐름은 작업 위험도에 따라 두 가지다.

- **Fast Lane**: `사용자 요구 → ChatGPT 기획/범위확정 → Issue → Claude 개발/테스트 → PR → ChatGPT 검토 → Done`
- **Approval Lane**: `사용자 요구 → ChatGPT 기획 → Issue → Claude 기술검토 → 사용자 승인 → 개발/테스트 → PR → Review → Done`

## 2. 기본값: Fast Lane
다음 조건을 모두 만족하면 사용자에게 매 단계 승인을 다시 받지 않고 진행한다.

- 요구사항과 완료 기준이 명확함
- 기존 서비스 방향을 바꾸지 않음
- 유료 서비스/API를 새로 도입하지 않음
- 회원가입/개인정보/결제/권한 구조를 건드리지 않음
- URL/SEO/데이터 모델/배포 구조를 대규모로 바꾸지 않음
- 삭제·마이그레이션 같은 파괴적 변경이 아님
- 롤백이 어렵지 않은 소규모 기능/버그/UI/콘텐츠/QA 변경

Fast Lane에서는 ChatGPT가 기획 범위를 확정한 뒤 Claude에게 바로 개발을 맡길 수 있다. Claude가 코드를 읽다가 사용자 결정이 필요한 문제를 발견하면 그때만 `NEEDS DECISION`으로 멈춘다.

ChatGPT도 GitHub 쓰기 권한과 검증 수단이 충분한 저위험 작업이라면 직접 수정할 수 있다. 다만 실제 실행환경/브라우저 QA/로컬 빌드가 중요한 개발은 Claude에게 맡기는 것을 우선한다.

## 3. Approval Lane으로 올려야 하는 작업
다음은 사용자 승인 없이 진행하지 않는다.

- 핵심 화면/사용자 흐름을 크게 바꾸는 리디자인
- 기능 삭제 또는 제품 방향 변경
- 유료 API/서비스/예상 유지비 증가
- 개인정보/회원가입/결제/인증/권한
- 데이터 모델의 큰 변경 또는 마이그레이션
- 기존 URL/SEO 구조의 대규모 변경
- 배포/인프라 구조의 큰 변경
- 대량 삭제, 되돌리기 어려운 변경
- 여러 핵심 파일/기능이 동시에 얽혀 영향 범위가 큰 작업
- Claude/ChatGPT가 사용자 취향·사업 판단이 필요하다고 판단한 작업

## 4. ChatGPT가 기획을 끝냈을 때
1. 필요한 경우 기획안을 Markdown으로 저장한다.
   - 기능/UX: `docs/product/`
   - 콘텐츠: `docs/content/`
   - SEO: `docs/seo/`
   - QA: `docs/qa/`
2. 기존 코드·문서·Issue와 중복 여부를 확인한다.
3. 개발 작업은 가능한 경우 Issue로 관리한다.
4. Issue에 목적, 범위, 제외범위, 완료기준을 적는다.
5. 위험도를 판단해 `FAST LANE` 또는 `APPROVAL REQUIRED`를 명시한다.

## 5. Claude가 Issue를 받았을 때
Claude는 다음을 먼저 확인한다.

1. `AGENTS.md`
2. `CLAUDE.md`
3. `docs/PROJECT_STATE.md`
4. 관련 Issue
5. 연결된 기획문서
6. 관련 코드와 최근 PR

### Fast Lane 작업
- 사용자 결정이 필요 없으면 바로 구현한다.
- 개발 전 짧게 충돌/영향 범위를 확인한다.
- 구현, 테스트, PR까지 한 번에 진행한다.
- 문제가 생길 때만 `NEEDS DECISION` 또는 `BLOCKED`로 멈춘다.

### Approval Lane 작업
먼저 아래 중 하나를 기록한다.

#### READY FOR APPROVAL
- 구현 가능
- 기존 구조와 큰 충돌 없음
- 권장 구현방법과 예상 변경영역 제시
- 사용자 승인 대기

#### NEEDS DECISION
- 질문은 1~3개로 줄인다.
- 가능한 경우 `A / B / 추천안 / 이유` 형식으로 작성한다.
- 답변 전까지 해당 개발을 중단한다.

#### BLOCKED
- 코드, 환경, 권한, 외부 의존성 등으로 진행이 불가능함
- 부족한 것과 다음 행동을 명확히 적는다.

## 6. 승인 규칙
Fast Lane은 별도 사용자 승인 문구 없이 진행할 수 있다.

Approval Lane은 다음 중 하나가 명확히 기록되어야 개발을 시작한다.
- `개발 승인`
- `APPROVED`
- 사용자가 ChatGPT에 명시적으로 승인하고 ChatGPT가 Issue에 승인 사실을 기록

ChatGPT는 저위험 작업에 대해 `FAST LANE APPROVED`를 기록하고 바로 Claude에게 진행시킬 수 있다.

## 7. 개발 단계
1. 가능한 경우 Issue 번호와 연결된 전용 branch 사용
2. 최신 `main` 반영 및 충돌 확인
3. 구현
4. 테스트/QA
5. PR 생성
6. PR에 다음을 기록
   - 무엇을 바꿨는지
   - 테스트 결과
   - 기획안과 달라진 점
   - 남은 위험/후속작업
7. 운영 배포 여부는 작업별 배포 규칙을 따른다.

## 8. Claude가 임의로 결정해도 되는 범위
기획 의도를 바꾸지 않는 한 다음은 개발자가 합리적으로 판단할 수 있다.
- 변수명/함수명
- 내부 파일 분리
- 동등한 구현 방식 중 단순한 선택
- 코드 포맷팅
- 테스트 구조
- 명백한 버그 수정
- 기존 컴포넌트/함수 재사용
- 소규모 반응형 보정

사용자 판단이 필요한 항목은 3절 기준을 따른다.

## 9. 사용자가 GitHub를 직접 보지 않아도 되는 운영
사용자는 ChatGPT에 요구사항만 말해도 된다. ChatGPT가 필요에 따라 GitHub Issue/문서/댓글을 만들고 Claude에게 넘길 수 있다.

Fast Lane에서는 사용자가 중간 전달자가 되지 않는 것을 목표로 한다. 사용자는 주로 다음 경우에만 개입한다.
- 제품/사업 방향 결정
- 디자인 선택
- 비용/서비스 도입 결정
- 되돌리기 어려운 변경 승인
- 최종 결과 확인

## 10. 운영 원칙
- 한 Issue = 한 실행 Claude를 기본으로 한다.
- 한 작업 = 전용 branch를 우선한다.
- 다른 Claude가 진행 중인 작업을 덮어쓰지 않는다.
- 중요한 결과는 GitHub에 남긴다.
- 운영 배포 완료 여부는 소스 반영 여부와 분리해 기록한다.

## 11. 자동화 방향
초기 파일럿에서 협업 절차가 검증되었으므로, 이후에는 승인 왕복을 줄이는 것을 우선한다.

장기적으로는 Issue/PR 기반 자동 알림과 병렬 Claude 운영을 확대할 수 있지만, 자동화 자체보다 **사용자에게 올라가는 결정의 수를 줄이는 것**을 우선한다.
