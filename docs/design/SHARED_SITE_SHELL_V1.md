# Shared Site Shell v1 — Header / Navigation / Language

## Status
**DESIGN PREP — USER REVIEW PENDING — DO NOT IMPLEMENT YET**

## 1. Why this is needed
The redesigned homepage and work-detail pages now share a coherent visual language, but utility/static pages still use older page-local headers and language treatments.

Current examples:
- homepage/map shell in `site/index.html` / `contentmap_style.css`
- work-detail shell generated by `site/generate_work_pages.js`
- Places hub in `site/places/index.html`
- Regions hub in `site/regions/index.html`

This creates a risk that users feel they have entered a different site when moving between homepage, work detail, map, places, and regions.

## 2. Goal
Create a small, reusable **site shell language**, not a large framework rewrite.

Users should always recognize:
- where they are
- how to return home
- how to reach the map/discovery surface
- what language is active

The shell must adapt to page type without forcing identical layouts everywhere.

## 3. Three shell variants

### A. Cinematic shell
Use for:
- homepage hero context
- work-detail top hero when image/emotion is primary

Traits:
- dark background
- high-contrast logo/text
- coral active/primary state
- compact language control

### B. Utility light shell
Use for:
- places hub
- regions hub
- place detail reading/travel sections
- about/contact/privacy/terms where applicable

Traits:
- warm-white/light surface
- subtle bottom border
- dark text
- same logo geometry
- same language control anatomy

### C. Map/app shell
Use for:
- full-height map

Traits:
- compact dark header
- minimal vertical footprint
- do not steal map space
- same logo/language anatomy
- contextual home/back action only where useful

## 4. Navigation principle
Do not invent routes only to make the header look complete.

Only show globally stable existing destinations.

Recommended priority:
1. brand/logo → home
2. map/discovery entry
3. places
4. regions
5. contextual current-work/place action when relevant

Quiz should remain contextual until a genuine site-wide quiz hub exists.

If a `works` collection route is not actually available and stable, do not create a fake global `작품` nav item as part of this visual task.

## 5. Language switcher
Canonical visual labels:
- KR
- EN
- JP
- 繁中

Rules:
- active language visibly selected
- disabled/unavailable translation must use the established i18n readiness behavior, not silent fallback
- long navigation/localized labels must not break layout
- language switcher touch targets >=44px on mobile where space permits; compact control may use a menu only if direct four-language display is impossible
- preserve existing hreflang/route logic; this is presentation consistency, not locale architecture rewrite

## 6. Desktop anatomy
Recommended height range: 64–72px depending on page type.

Left:
- logo mark + `그곳, 지금`

Middle/right:
- existing stable primary destinations

Far right:
- language switcher
- optional contextual Home/Back only when it avoids user confusion

Avoid duplicating `logo → home` and a visually equally strong `홈` control side by side unless the page type genuinely benefits from both.

## 7. Mobile anatomy
Target: 360 / 390 / 430px.

Preferred:
- logo/brand left
- one compact navigation/menu control when needed
- language access right

Do not wrap the header into two accidental rows because translated labels are wider.

If four language pills and nav cannot coexist, preserve language access and collapse secondary navigation rather than shrinking controls below accessible size.

## 8. Visual tokens
Reuse existing approved system:
- dark shell background: `#0A0B0F` / `#141820` family
- light shell: warm white/off-white
- primary accent: `#FF7B57`
- dark text on light: near-black
- light text on dark: white / `#CDD2DC`
- border: `#242A34` dark, warm-light neutral on light

No new competing brand color system.

## 9. Preserve
- current URLs
- existing link targets
- KR / EN / JP / zh-Hant routes
- PR #16 i18n behavior
- SEO metadata
- map app state/deep-link behavior
- page-specific sticky/full-height behavior

## 10. Implementation principle
Prefer shared CSS tokens/classes or generator-level reuse where practical, but do not force a framework migration.

If current static generators make a shared partial impractical, consistent duplicated markup is acceptable before architecture work.

This design task should not become a templating-engine rewrite.
