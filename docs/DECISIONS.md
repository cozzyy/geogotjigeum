# DECISIONS — 그곳지금

프로젝트의 중요한 방향 변경을 기록한다. 단순 작업 로그는 Issues/PR에 남기고, 여러 사람·AI가 앞으로도 알아야 할 결정만 이 문서에 기록한다.

---

## 2026-08-26 — GitHub를 Single Source of Truth로 사용

### 결정
그곳지금 프로젝트의 코드, 기획문서, 작업상태, 의사결정 및 AI 인수인계의 중심을 GitHub로 통일한다.

### 이유
ChatGPT, Claude, Manus, 외부 개발자가 서로 다른 계정과 채팅을 사용해도 동일한 프로젝트 상태를 공유할 수 있어야 하기 때문이다.

### 영향
- AI는 작업 시작 전 GitHub 최신 상태를 확인한다.
- 중요한 작업은 GitHub Issue로 관리한다.
- 진행상태는 GitHub Projects로 관리한다.
- 결과물은 Repository에 남긴다.
- 대화 기억은 보조수단이며 최종 기록으로 간주하지 않는다.

## 2026-08-26 — 별도 Notion을 우선 도입하지 않음

### 결정
초기 AI 공동개발 시스템 v1에서는 Notion/Airtable 등 별도 PM 도구를 필수 구성요소로 추가하지 않는다.

### 이유
동일 정보가 여러 곳에 존재해 최신본 판단이 어려워지는 것을 피하고, 개발·문서·작업 관리를 GitHub 중심으로 단순화하기 위함이다.

### 재검토 조건
사람 중심의 위키/대시보드 기능이 GitHub만으로 명확히 부족해질 경우 재검토한다.

## 2026-08-26 — GitHub Projects와 서비스 DB의 역할 분리

### 결정
GitHub Projects는 개발/콘텐츠/운영 작업 상태 DB로 사용한다. 실제 사용자·촬영지·작품·리뷰 등 서비스 운영 데이터는 필요 시 별도의 PostgreSQL/Supabase 계열 서비스 DB를 사용한다.

### 이유
GitHub Projects는 업무 추적에 적합하지만 대량의 서비스 데이터 저장·조회용 DBMS는 아니기 때문이다.

## 2026-08-26 — 대표 승인 중심의 AI 운영 구조를 단계적으로 구축

### 결정
그곳지금의 향후 자동화는 GitHub를 기준본으로 유지하고, AI가 대표 의사결정용 요약·선택지·권고안을 만들며, 대표 승인 후에만 실행 단계로 넘어가는 구조로 설계한다. n8n은 정보 수집·알림·상태 연결에 사용한다. Notion 등 별도 현황판은 GitHub 기반 요약 화면이 실제로 필요해질 때만 도입한다.

### 이유
코드·문서·작업 이력을 여러 도구에 중복 저장하지 않으면서도, 대표가 복잡한 작업 목록 대신 결정이 필요한 안건만 빠르게 검토할 수 있어야 하기 때문이다.

### 영향
- 승인 전 자동 개발·자동 배포·대외 발송은 금지한다.
- 첫 단계는 GitHub Projects와 수동 승인 규칙 정착이다.
- 이후 주간 보고 초안, Inbox 수집, 승인 후 실행 연결 순서로 확대한다.
- 상세 실행 기준은 `docs/product/representative-approval-automation-blueprint-v1.md`, 추적 Issue는 #8을 사용한다.

### 재검토 조건
대표 현황판의 사용성 또는 자동 보고 정확도가 부족할 때, Notion 등 별도 요약 UI를 추가 검토한다.

## 2026-08-26 — ChatGPT 기획자 / Claude 개발자 기본 역할과 승인 Gate

### 결정
ChatGPT는 기본적으로 기획자와 사용자 의사결정 지원 역할을 맡고, Claude는 기술검토자와 개발자 역할을 맡는다. 개발이 필요한 기획은 GitHub의 기획문서와 Handoff Issue로 전달하며, Claude는 구현 전에 기술검토를 수행한다. 중요한 개발은 사용자의 명시적 승인 후 시작한다.

### 이유
서로 다른 AI 채팅과 계정 사이의 기억 공유에 의존하지 않고, 기획 의도·기술 검토·사용자 결정·개발 결과를 GitHub에 일관되게 남기기 위함이다.

### 영향
- ChatGPT가 기획 완료 후 GitHub에 문서와 Handoff Issue를 남긴다.
- Claude는 `READY FOR APPROVAL / NEEDS DECISION / BLOCKED` 중 하나로 검토 결과를 남긴다.
- 사용자 판단이 필요한 경우 Claude가 선택지와 추천을 제시하고 개발을 멈춘다.
- `개발 승인` 또는 `APPROVED`가 기록된 뒤 개발한다.
- 세부 절차는 `docs/CHATGPT_CLAUDE_HANDOFF.md`를 기준으로 한다.

### 재검토 조건
수동 Handoff 2~3건을 실제 운영한 뒤 불필요한 승인 단계나 반복 질문이 많으면 규칙을 단순화하고 자동화 범위를 재설계한다.

## 2026-08-27 — 저위험 개발은 Fast Lane으로 전환

### 결정
Issue #10과 #17 파일럿을 통해 GitHub 기반 협업 절차가 검증되었으므로, 앞으로 저위험·명확한 개발은 사용자에게 기술검토와 승인 요청을 매번 왕복하지 않고 ChatGPT가 범위를 확정한 뒤 Claude가 바로 구현·테스트·PR까지 진행한다. ChatGPT도 GitHub 쓰기 권한과 검증 수단이 충분한 저위험 작업은 직접 수행할 수 있다.

### 이유
개발할 항목이 많은 상황에서 모든 작업을 `기획 → 기술검토 → 사용자 전달 → 승인 → 개발` 순으로 반복하면 대표의 시간이 과도하게 소모되고 개발 속도가 느려진다. 사용자는 사업·제품 방향과 되돌리기 어려운 결정에 집중하는 것이 더 효율적이다.

### 영향
- 소규모 기능, 버그, UI 보정, 콘텐츠/QA, 내부 리팩터링은 Fast Lane을 기본으로 한다.
- Fast Lane에서는 Claude가 최신 `main`/충돌만 확인한 뒤 바로 개발·테스트·PR까지 진행한다.
- 사용자 결정이 실제로 필요한 문제가 생길 때만 `NEEDS DECISION`으로 멈춘다.
- 큰 리디자인, 유료 서비스, 개인정보/결제/인증, 대규모 데이터·URL·SEO·배포 구조 변경, 파괴적 변경은 기존 승인 Gate를 유지한다.
- 상세 기준은 `docs/CHATGPT_CLAUDE_HANDOFF.md`와 `CLAUDE.md`를 따른다.

### 재검토 조건
Fast Lane에서 회귀 버그, 범위 초과, 병렬 충돌이 반복될 경우 승인 기준을 다시 강화한다.

## 2026-08-27 — 홈페이지 디자인은 Cinematic Content Discovery 방향으로 확정

### 결정
그곳지금 홈페이지의 1차 디자인 방향을 **A. Cinematic Content Discovery**로 확정한다. 어두운 시네마틱 배경, 이미지 중심 구성, 따뜻한 coral accent, `장면 → 작품 → 실제 장소 → 여행` 흐름을 기본 UX로 사용한다.

### 이유
현재 사이트의 기능 중심·개발자형 화면보다 작품의 감정과 장면을 먼저 보여주는 방식이 그곳지금의 핵심 가치인 K-content 장소 발견을 더 빠르고 직관적으로 전달하기 때문이다.

### 영향
- 공식 최소 디자인 기준은 `docs/design/DESIGN_SYSTEM_V1.md`를 따른다.
- 홈페이지 구현 기준은 `docs/design/HOMEPAGE_REDESIGN_A_V1.md`를 따른다.
- 개발 추적은 Issue #19를 사용한다.
- 기존 KR/EN/JP/ZH, URL/SEO, 지도/데이터 구조는 이번 리디자인으로 변경하지 않는다.
- 홈페이지 검증 후 후킹페이지·지도·퀴즈 등으로 디자인 시스템 적용 범위를 단계적으로 확장한다.

### 재검토 조건
홈페이지 실제 배포 후 모바일 사용성, 이탈, 탐색성 또는 사용자 피드백에서 문제가 확인될 때 수정한다.
