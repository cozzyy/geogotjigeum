# 폭싹 속았수다 퀴즈 결과 — 촬영지 3곳 카드 파일럿 v1

작성일: 2026-08-27

## 1. 목적
이 작업은 기능 자체보다 **사용자 + ChatGPT 기획자 + Claude 개발자**가 GitHub를 공용 작업공간으로 사용하는 첫 3자 협업 파일럿이다.

작고 독립적이며 눈으로 결과를 확인하기 쉬운 기능으로 `기획 → 기술검토 → 사용자 승인 → 개발 → 테스트 → PR/인수인계` 흐름을 검증한다.

## 2. 대상
기존 **〈폭싹 속았수다〉 퀴즈의 완료/결과 화면**만 개선한다.

현재 퀴즈 구현의 정확한 파일 위치와 기존 기능 상태는 Claude가 코드/로컬 운영본을 확인해 기술검토에서 확정한다. GitHub 검색만으로 구현 파일이 명확히 확인되지 않으므로 ChatGPT가 파일명을 추정하지 않는다.

## 3. 사용자 기능
퀴즈를 모두 푼 뒤 결과 화면에서 다음을 제공한다.

1. 기존 점수/결과는 그대로 유지
2. 점수 아래에 **이 작품의 촬영지 3곳** 카드 노출
3. 각 카드에는 최소 다음을 표시
   - 장소명
   - 작품/장면과 연결되는 짧은 한 줄
   - `장소 보기` CTA
4. `장소 보기`는 이미 존재하고 검증된 그곳지금 장소 페이지/데이터로 연결
5. **`다시 풀기`** 버튼 제공
6. 다시 풀기 시 1번 문제부터 재시작하고 기존 선택/점수/완료상태를 초기화

## 4. 장소 3곳 선정 원칙
- 새 장소나 URL을 임의로 만들지 않는다.
- 현재 사이트/데이터에 존재하는 〈폭싹 속았수다〉 관련 **검증된 촬영지 3곳**을 사용한다.
- Claude 기술검토 단계에서 장소명과 실제 연결 URL/데이터 키를 제시한다.
- 3곳은 가능하면 서로 다른 장면/지역 또는 여행 가치가 드러나도록 선정한다.

## 5. 모바일 우선
PC보다 모바일 결과 화면을 먼저 설계한다.

필수 확인 폭:
- 360px
- 390px
- 430px

원칙:
- 결과 점수 → 장소 3곳 → 다시 풀기/다음 행동의 우선순위가 명확할 것
- 카드가 작은 화면에서 가로 넘침을 만들지 않을 것
- CTA 터치 영역이 충분할 것
- 장소 카드 3개 때문에 결과 화면이 과도하게 길거나 답답해지지 않을 것
- 기존 퀴즈 스타일을 최대한 재사용하고 새 전역 CSS 의존을 최소화할 것

## 6. 이번 파일럿에서 하지 않을 것
이번 작업은 작게 유지한다.

- 퀴즈 20문제 신규 작성/확장은 하지 않음
- 기존 질문/정답/점수 계산을 변경하지 않음
- 공통 퀴즈 아키텍처 전체 리팩터링 안 함
- 로그인/랭킹/공유/서버 저장 추가 안 함
- 프레임워크 교체 안 함
- 백엔드 추가 안 함
- 전 작품 퀴즈 일괄 적용 안 함
- Issue #10 다국어/i18n 구조를 수정하지 않음

## 7. Issue #10과 충돌 방지
현재 Issue #10의 다국어 작업은 별도 Claude가 진행할 수 있으므로 파일 충돌을 피한다.

Issue #10 검토에서 예상된 주요 범위:
- `contentmap_i18n.js`
- `contentmap_app.js`
- `generate_work_pages.js`
- `generate_place_pages.js`
- `generate_region_pages.js`
- `index.html`
- `contentmap_prototype.html`
- `contentmap_style.css`
- `generate_lang_shells.js`
- `sitemap.xml`

이 파일들, 특히 전역 `contentmap_style.css` 수정이 필요하다면 바로 개발하지 말고 충돌 가능성을 기술검토에 보고한다. 가능한 경우 **퀴즈 전용 파일/스타일 안에서만** 구현한다.

## 8. Claude 기술검토에서 반드시 확인할 것
아직 구현하지 말고 다음을 먼저 보고한다.

1. 현재 〈폭싹 속았수다〉 퀴즈 구현 파일/경로
2. 현재 완료 화면에 이미 있는 기능(재시도/장소 CTA 등) 여부
3. 이 기획의 구현 가능 여부
4. 정확한 예상 변경 파일
5. Issue #10과 파일/기능 충돌 여부
6. 사용할 기존 촬영지 3곳의 장소명 + 실제 URL 또는 데이터 키
7. `다시 풀기` 시 초기화할 state 목록과 구현 방식
8. 360/390/430px 모바일 검증 계획
9. 기존 퀴즈 질문/점수 로직 회귀 테스트 계획

결과는 다음 중 하나로 보고한다.
- `READY FOR APPROVAL`
- `NEEDS DECISION`
- `BLOCKED`

## 9. 완료 기준
- [ ] 기존 퀴즈 질문/정답/점수 계산이 바뀌지 않음
- [ ] 퀴즈 완료 뒤 촬영지 카드 정확히 3개가 표시됨
- [ ] 3개 모두 실제 존재하는 장소 페이지/데이터로 연결됨
- [ ] `다시 풀기`가 1번 문제로 돌아가고 점수/선택/완료 상태를 초기화함
- [ ] 360/390/430px에서 레이아웃과 터치 동작 정상
- [ ] Issue #10 작업 파일과 충돌 없음 또는 충돌이 사전에 승인됨
- [ ] 테스트 결과가 Issue/PR 인수인계에 기록됨
- [ ] 운영 배포는 별도 승인/인수인계 절차를 따름

## 10. 개발 승인 상태
**NOT APPROVED**

Claude는 기술검토까지만 수행한다. 사용자의 `개발 승인` 또는 `APPROVED`가 기록되기 전에는 구현을 시작하지 않는다.

## 11. 이 파일럿에서 확인하려는 협업 자체의 성공 기준
- ChatGPT가 기획문서와 Handoff Issue를 GitHub에 남긴다.
- Claude가 GitHub 기준 문서와 기획을 읽고 기술검토를 작성한다.
- Claude가 GitHub 댓글을 직접 못 쓰는 환경이면 `GitHub Issue 댓글용` 완성문을 사용자에게 출력한다.
- 사용자는 Claude 답변을 ChatGPT에 전달한다.
- ChatGPT가 실제 Issue에 검토내용을 기록하고 기획 관점에서 판단한다.
- 사용자가 승인 여부만 결정한다.
- 승인 후 Claude가 개발·테스트 결과를 인수인계한다.

이 파일럿에서는 기능 품질뿐 아니라 **누가 무엇을 어디에 기록하는지**가 잘 작동하는지도 함께 평가한다.
