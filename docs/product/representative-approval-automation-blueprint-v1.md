# 대표 승인 기반 AI 운영·자동화 설계 v1

작성일: 2026-08-26  
상태: 설계 완료 · **Hold**  
실행 시작 조건: 사용자가 “자동화하자”라고 명시할 때

## 1. 목표

그곳지금의 개발·콘텐츠·SEO·QA·운영 정보를 자동으로 모으고, AI가 대표의 의사결정에 필요한 내용만 짧게 요약한다. 대표가 승인·보류·수정 요청을 하면 승인된 작업만 실제 개발·검토·배포 흐름으로 들어가도록 한다.

대표가 매일 여러 도구를 확인하거나 작업을 직접 관리하지 않아도 되는 구조를 목표로 한다.

## 2. 기본 원칙

- GitHub `cozzyy/geogotjigeum`은 코드·문서·Issue·PR·결과의 **Single Source of Truth**다.
- 대표 현황판은 사람이 보기 위한 요약·결정 화면이며, 원문과 최종 상태를 대체하지 않는다.
- n8n은 정보 수집·알림·상태 전환을 연결하는 자동화 도구다.
- AI는 요약·우선순위·선택지·권고안을 만들지만, 비용·배포·대외 공개 등 중요한 실행은 대표 승인 후 진행한다.
- 비밀정보·API 키·개인정보는 GitHub Issue, 현황판, 자동 보고에 남기지 않는다.
- 자동화는 처음부터 전체를 연결하지 않고, 확인 가능한 작은 흐름부터 단계적으로 도입한다.

## 3. 역할 분리

| 구성요소 | 맡는 일 | 기준 데이터 |
| --- | --- | --- |
| GitHub | 코드, 문서, Issue, PR, 변경 이력, 완료 근거 | 공식 기준본 |
| GitHub Projects | 작업 상태·우선순위·담당·검토 흐름 | 업무 상태 DB |
| AI (ChatGPT 등) | 요약 보고, 기획 초안, 영향 분석, QA 의견, 후속 Issue 초안 | GitHub 및 승인된 외부 데이터 |
| n8n | 수집, 감지, 알림, 승인 상태에 따른 다음 단계 실행 | 자동화 연결선 |
| 대표 현황판 | 결정 필요 항목, 권고안, 승인·보류·수정 요청 | GitHub를 읽는 요약 화면 |
| Claude / Manus / 개발자 | 승인된 구현, 테스트, PR, 배포 준비 | GitHub Issue·PR |

## 4. 목표 운영 흐름

```text
메일·회의·사이트 오류·검색 데이터·AI 아이디어
                    ↓
             n8n 수집 / Inbox 등록
                    ↓
       AI 중복 확인·분류·우선순위·권고안 작성
                    ↓
 GitHub Issue + 대표 현황판의 “결정 필요” 카드
                    ↓
       대표: 승인 / 수정 요청 / 보류 / 반려
                    ↓
  승인된 Issue만 개발·콘텐츠·SEO·QA 담당에게 배정
                    ↓
        구현 → PR → AI/담당자 QA → 배포 승인 요청
                    ↓
         배포 → 결과 측정 → 대표 요약 보고 → GitHub 기록
```

## 5. 대표가 보는 최소 화면

대표 현황판에는 전체 업무가 아니라 **결정을 요하는 항목만** 노출한다.

| 항목 | 표시 내용 |
| --- | --- |
| 결정 제목 | 무엇을 결정해야 하는가 |
| 한 줄 요약 | 지금 필요한 이유 |
| AI 권고안 | 권장 선택지와 근거 |
| 선택지 | 승인 / 수정 요청 / 보류 / 반려 |
| 예상 영향 | 사용자·SEO·비용·일정·위험 |
| 근거 | 관련 Issue, 문서, 데이터, QA 결과 |
| 실행 상태 | 승인 대기 / 진행 중 / QA 검토 / 배포 승인 대기 / 완료 |
| 결과 | PR, 배포 링크, 지표 변화 |

대표는 원칙적으로 위 네 가지 선택만 한다.

- **승인:** 실행 가능한 Issue로 전환
- **수정 요청:** AI가 선택지·범위·자료를 보완해 재보고
- **보류:** 외부 조건 또는 우선순위가 바뀔 때까지 중단
- **반려:** 진행하지 않음. 사유를 기록해 재제안 방지

## 6. GitHub 상태·승인 규칙

GitHub Project의 기본 상태는 다음을 사용한다.

`Inbox → Planned → Todo → In Progress → Review → Done`

대표 승인 흐름은 상태와 별도로 다음 정보를 가진다.

| 승인 상태 | 의미 | 다음 자동 행동 |
| --- | --- | --- |
| Decision Needed | 대표 판단이 필요한 안건 | 대표 현황판·알림에 표시 |
| Approved | 범위와 우선순위가 승인됨 | Todo 전환, 담당 AI/개발자 작업 시작 |
| Changes Requested | 수정 후 재보고 필요 | AI가 보완안 작성 |
| Hold | 지금은 진행하지 않음 | 자동 실행 중지, 재검토 시점만 추적 |
| Rejected | 진행하지 않음 | Cancelled 처리 및 사유 보존 |

초기에는 GitHub Labels 또는 Project 필드 하나로 위 값을 관리한다. 별도의 데이터베이스를 먼저 만들지 않는다.

## 7. 단계별 도입 계획

### Phase A — 수동 승인 구조 정착

목표: 도구 자동 연결 전에도 대표 승인 규칙이 일관되게 작동하게 한다.

- [ ] GitHub Project 생성 및 상태·우선순위·승인 필드 설정 (Issue #2)
- [ ] 대표 판단이 필요한 Issue에 `Decision Needed` 표시
- [ ] AI가 Issue마다 ‘요약 / 선택지 / 권고안 / 영향 / 완료 기준’을 작성
- [ ] 대표가 GitHub 또는 요약 보고에서 승인·보류·수정 요청
- [ ] 승인된 항목만 `Todo` 또는 `In Progress`로 전환
- [ ] 배포·대외 공개는 별도 최종 승인 단계 유지

완료 기준: 최소 3건의 실제 안건이 승인 → 실행 → QA → 결과 기록 흐름을 거친다.

### Phase B — 대표 주간 보고 자동화

목표: 대표가 현재 상태와 결정 필요 항목을 정기적으로 한 번에 확인한다.

입력:
- 열린 P0/P1 Issue
- Hold·막힘 상태
- 이번 주 완료 Issue·PR
- QA 결과
- 배포 결과
- Search Console·GA4 등 연결 가능한 핵심 지표

출력:
- 이번 주 결정 필요 최대 3~5건
- 승인된 작업 진행률
- 막힌 이유와 필요한 조치
- 배포·SEO·콘텐츠 성과 요약
- 다음 주 권고 우선순위

n8n은 정해진 주기에 GitHub 정보를 가져오고, AI가 보고 초안을 만든다. 초기에는 자동 발송 대신 검토용 초안을 먼저 만든다.

완료 기준: 주간 보고 초안이 GitHub의 실제 상태와 일치하고, 대표 확인 후 발송 또는 현황판 게시가 가능하다.

### Phase C — Inbox 자동 수집

목표: 메일·회의·메모·오류·아이디어를 사람이 다시 정리하지 않아도 작업 후보로 만든다.

우선 입력:
1. 대표가 던지는 채팅·메모
2. GitHub Issue/PR/배포 이벤트
3. 사이트 오류 및 QA 결과
4. Search Console·GA4 핵심 변화
5. 이메일·회의록 (연결 권한과 개인정보 범위를 별도 검토한 후)

처리:
- 원문 보존
- 기존 Issue·문서 중복 검색
- Type / Priority / Area / Source 제안
- 실행 가치와 대표 승인 필요 여부 판단
- `Inbox` 또는 `Decision Needed` 등록

완료 기준: 실제 입력 5건 이상이 누락 없이 Inbox → 판단 → 실행/보류 흐름을 통과한다.

### Phase D — 승인 후 실행 자동 연결

목표: 승인된 작업만 담당 에이전트에게 전달하고, 결과를 다시 보고한다.

- `Approved` 전환 감지
- Issue 내용·관련 문서·완료 기준을 담당 에이전트에 전달
- 담당 에이전트는 Branch/PR/결과 문서를 GitHub에 남김
- QA 조건 충족 시 `Review`로 전환
- 배포 승인 필요 항목은 다시 `Decision Needed`로 대표에게 보고
- 최종 완료 시 PR·배포·측정 결과를 Issue와 현황판에 연결

초기에는 자동 코드 수정·자동 배포를 금지한다. 승인된 Issue의 **작업 시작과 보고 생성**만 자동화하고, PR 병합·프로덕션 배포는 사람 승인 단계를 유지한다.

## 8. 권장 기술 조합

| 단계 | 최소 구성 | 확장 구성 |
| --- | --- | --- |
| Phase A | GitHub Issues + GitHub Projects + AI | 동일 |
| Phase B | GitHub + n8n + AI 주간보고 초안 | 대표 현황판 추가 |
| Phase C | n8n + GitHub Inbox | Gmail·회의록·Analytics 연결 |
| Phase D | GitHub webhooks + n8n + AI | PR·QA·배포·성과 피드백 루프 |

Notion은 Phase B 이후에도 필수는 아니다. 대표가 GitHub Projects만으로 결정을 내리기 불편할 때, **GitHub 내용을 읽어오는 요약 현황판**으로만 도입한다. Notion에 원문 문서·코드·작업 이력을 중복 보관하지 않는다.

## 9. “자동화하자” 명령을 받았을 때의 실행 순서

새 에이전트는 아래 순서대로 진행한다.

1. `AGENTS.md`, `docs/PROJECT_STATE.md`, `docs/PROJECT_MANAGEMENT.md`, 이 문서, 열린 Issues를 읽는다.
2. 자동화의 범위를 확인한다. 예: 주간 보고만 / Inbox까지 / 승인 후 개발 연결까지.
3. Issue #2의 GitHub Project 보드·필드가 실제로 준비됐는지 확인한다.
4. 최신 운영 사이트 코드 저장소와 배포 환경이 확정됐는지 확인한다 (Issue #4).
5. 연결할 외부 서비스와 공유 가능한 데이터 범위·권한을 사용자에게 명확히 확인한다.
6. 가장 작은 Phase부터 Issue를 분리하고, 각 단계의 테스트·중단 조건을 정의한다.
7. n8n에는 읽기·초안 생성 자동화부터 구성한다. 처음에는 Issue 생성, 상태 변경, 배포를 자동 확정하지 않는다.
8. 대표 보고의 형식·발송 주기·승인 방법을 사용자와 확정한다.
9. 파일럿 결과를 GitHub에 기록하고, 정확도·누락·오작동을 검토한 뒤 다음 Phase로 진행한다.

## 10. 실행 전 확인 사항

- [ ] 운영 사이트 코드의 canonical repository와 배포 환경 확인 (#4)
- [ ] GitHub Project 보드와 승인 필드 설정 (#2)
- [ ] 대표가 승인하는 화면·방식 결정
- [ ] n8n 설치 또는 접근 권한 확인
- [ ] Gmail·Analytics·배포 서비스 연결 범위와 개인정보 처리 기준 결정
- [ ] 자동 실행 금지 범위 설정: 프로덕션 배포, 외부 메시지, 비용 발생 작업, 권한 변경
- [ ] 첫 파일럿 범위 선정: 주간 보고 또는 Inbox 중 하나

## 11. 성공 기준

- 대표는 한 화면 또는 한 보고에서 “결정 필요” 항목만 확인한다.
- 승인되지 않은 작업은 개발·배포로 자동 진입하지 않는다.
- 어떤 AI가 작업하더라도 근거·상태·결과는 GitHub에서 추적된다.
- 자동 보고의 사실관계가 GitHub와 실제 서비스 상태에 일치한다.
- 오류·변경·성과가 다음 기획 우선순위에 반영된다.
